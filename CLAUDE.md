# Lab job dispatcher

Node + Fastify service on this Mac mini that runs named jobs on request. Rules below are binding for every session. Start with `README.md` for the map of the repo; details are in `docs/`.

## Rules
- `POST /run/:job` runs `./jobs/<job>.sh` in its own process group with a 60s timeout; on expiry the whole group gets SIGKILL, so nothing the job started outlives it.
- Auth: Bearer token read from `~/.lab/token` (dir 700, file 600). The token never goes in the repo, in chat, in logs, or in the plist. The server refuses to start if the file is looser than 600.
- Job names must match `^[a-z0-9-]+$` and map only to executable regular files directly inside `./jobs/` (realpath-checked). No arbitrary commands, no shell, no request data passed to jobs.
- Listen on `127.0.0.1:8787` only. The host is hardcoded; do not add an env override or bind to 0.0.0.0.
- `GET /health` is the only unauthenticated route.
- Every request to `/run/:job` is logged to SQLite (`dispatcher.db`: job, source, start time, duration, exit code, status, output), including rejected ones.
- Runs as a LaunchAgent (`com.lab.dispatcher`, RunAtLoad + KeepAlive). Logs go to `~/Library/Logs/lab-dispatcher/`.
- `.gitignore` must keep covering `node_modules`, `*.db*`, `data/` (except `.gitkeep`), `config/slack-bus.json`, `config/slack-digest.json`, `config/digest-customers.json`, `docs/private/`, logs, and secrets. Never commit tokens.
- Changing any rule above needs the user's explicit approval. Tell the user when something needs sudo or a GUI click; do not work around it.

## Repository layout (keep it this way)
- `src/` service code; `jobs/` runnable jobs only; `launchd/` plist templates (the repo copy is the source of truth, installed via `scripts/install-agent.sh`); `scripts/` operator helpers; `config/` non-secret settings (real files with private details are git-ignored, with a tracked `*.example.json`); `data/` git-ignored runtime data; `docs/` documentation.
- Do not put code, plists or docs in the repo root. The root holds only `README.md`, `CLAUDE.md`, `package.json`, `package-lock.json`, `.gitignore`.

## Documentation rules
- Any change that adds, moves, renames or removes a file, job, schedule, endpoint, secret or setting must update the docs in the same commit: `README.md` (repository map), the relevant file in `docs/`, `jobs/README.md` (job and schedule table), and this file if a rule or convention changed.
- Every source file starts with a comment saying what it is and why it exists; every job script has a one-line purpose comment.
- Write for a newcomer: say what a thing does and why, not just how. Use plain names, and put design reasoning in `docs/decisions.md`.
- Never write secrets (token, ping URLs) into docs, examples or commit messages; refer to the `~/.lab/` file instead.

## Notes
- Node comes from Homebrew (`/opt/homebrew/bin/node`). SQLite uses the built-in `node:sqlite`, so there is no native dependency.
- Add a job by dropping an executable `jobs/<name>.sh`; no server change needed. Full steps: `docs/adding-jobs.md`.

## LLM helper for jobs
- Jobs call `node "$(dirname "$0")/../src/llm.js" <task> [options]` with the input text on **stdin** (never as an argument) and read the result on stdout. Full usage: `docs/adding-jobs.md`.
- Local tasks (Ollama `qwen2.5:7b` at `127.0.0.1:11434`, hardcoded): `classify --label name=description ...` (prints one label), `extract --fields a,b` (one-line JSON, null when absent), `summarize-short` (1-3 sentences). Any other task exits 3 with "needs cloud model"; do not add a cloud provider without the user's approval.
- Fixed limits: temperature 0.1, structured JSON output for classify and extract, per-task `num_predict` caps, 8,000-character input cap, 50s per call (`--timeout` may only lower it), `keep_alive: 1m` per request. Exit codes: 0 ok, 2 bad usage or input, 3 needs cloud model, 4 model error or timeout.
- Several calls in one job share the 60s job limit; pass a shrinking `--timeout` like `jobs/llm-test.sh` does.
- Never log, store or print input text (the helper doesn't, and a job must not echo it either), and never print the token.
- Prompt templates live in `src/llm-prompts.js`, each with 1-2 examples. After changing one, run `node scripts/llm-eval.js` and keep it passing.

## Scheduled jobs
- Schedules call the dispatcher; they never run job files directly. **One approved exception:** the Slack digest runs as its own launchd schedule (it takes minutes, over the 60s job limit); see `docs/decisions.md`. `src/schedule-run.js <job>` POSTs to `/run/<job>` (source `launchd-schedule`, so runs land in SQLite), then pings healthchecks.io: `GET <url>` on success, `<url>/fail` on any failure (dispatcher down, non-200, non-zero exit, timeout). The ping URL is read from `~/.lab/healthcheck-url-<job>` (one file per job, mode 600, never in the repo, logs, or chat); the wrapper fails without pinging if the file is missing or looser than 600.
- **Always prompt for a healthcheck URL.** Whenever the user asks for a new scheduled job (or a new job that will run on a schedule), do not create the plist or the schedule until you have told the user to create a new healthchecks.io check for it and put its URL in `~/.lab/healthcheck-url-<name>` (`umask 077; pbpaste > ~/.lab/healthcheck-url-<name>`, then chmod 600). Suggest a period and grace time that match the schedule. Never reuse another job's URL. Confirm the file exists with mode 600 before installing the schedule. A job that is only run on demand (no schedule) needs no check.
- To add a schedule: (1) the job must already exist as `jobs/<name>.sh`; (2) copy `launchd/com.lab.schedule.hello.plist` to `launchd/com.lab.schedule.<name>.plist`, change `Label`, the job argument, the `StartCalendarInterval`, and the log path; (3) create the job's own healthchecks.io check and write its URL to `~/.lab/healthcheck-url-<name>` (`umask 077`, chmod 600); (4) install it with `scripts/install-agent.sh launchd/com.lab.schedule.<name>.plist`.
- Test with `launchctl kickstart -k gui/$(id -u)/com.lab.schedule.<name>` and read `~/Library/Logs/lab-dispatcher/schedule-<name>.log`. Do not use `RunAtLoad` on schedules.
- The Mac must stay awake (`pmset` sleep 0; display sleep is fine) and logged in (auto-login is on). Missed runs fire on wake but are skipped if the Mac was powered off; the healthchecks grace period catches that.

## Slack measurement
- `scripts/slack-channels.js` and `scripts/slack-measure.js` (shared code in `src/slack.js`, also used by the digest) measure how many tokens a daily Slack digest would read. They run from the terminal, never through the dispatcher (too slow for the 60s limit). Full usage: `docs/slack-measurement.md`.
- The Slack user token is read only from `~/.lab/slack-token` (mode 600, enforced). Never print it, log it, put it on a command line or in an env var, or commit it.
- Read-only Slack calls only with the user token. The reading client (`src/slack.js`) refuses any method not in its list (`conversations.list/history/replies/members`, `users.list`); do not add a method that writes to Slack. Sending is only the digest DM, through the separate bot-token client `src/slack-send.js` (see Slack digest).
- Never write, log or print message text. Only per-channel, per-day counts go to `data/` (git-ignored, files written mode 600).
- Business-unit rules are in `config/slack-bus.json` (git-ignored; template `config/slack-bus.example.json`). Keep real channel IDs, unit names and people's names out of the repo, including docs and examples.
- Group DMs are assigned only by ID, with the full member set recorded, never by a partial sidebar name. If a name fits more than one group DM, or none, put it in `pendingGroupDms` and ask the user; do not guess. Check rule changes with `node scripts/slack-channels.js --from-cache` (no Slack calls).

## Slack digest
- Design and phases: `docs/slack-digest-design.md`; how to run it: `docs/slack-digest.md`. Each phase is built only after the user approves it. Workspace-specific notes and open questions: `docs/private/` (git-ignored).
- **Cloud models (approved by the user for the digest only):** OpenRouter, through `src/openrouter.js`, nothing else. Routes are in `config/slack-digest.json` (`models`): primary DeepSeek V3.2 pinned to DeepInfra, secondary Gemini Flash pinned to Google Vertex. Every request pins its provider with `allow_fallbacks: false`, `require_parameters: true` and `data_collection: "deny"`. After a timeout, 5xx or 429 the primary is retried once after a short backoff (about 3 s; Retry-After honored up to 10 s); then, after a timeout, 5xx, 429 or served-provider mismatch, the secondary is tried once. Never more than three requests per call (primary, primary retry, secondary). Retry and fallback reasons are recorded as error codes only. The served provider is checked after every call. Reasoning is off by default (Gemini uses its lowest level, since it cannot turn reasoning off). The key is read only from `~/.lab/openrouter-key` (mode 600); never print, log or commit it, or put it on a command line or in an env var. `src/llm.js` stays local-only.
- **Caps:** 400,000 estimated input tokens per run, 100,000 per call (well under DeepSeek V3.2's 163,840-token context), 60,000 output tokens and $0.50 per run. Over the run cap, customers go first, then sub-groups, busiest first, and the rest are marked "not summarized (cap)" with counts; the run does not abort. A call over the per-call cap keeps its newest messages.
- Phase 2 (model analysis), phase 3 (schedule and Slack DM delivery) and the redesign (customer registry, synthesis, noise rules, unit modes, two-part DM) are approved and built. Prompts live in `src/digest/prompts.js`; after changing one, run `node scripts/digest-eval.js` and keep the primary route passing (the secondary is informational). `scripts/model-check.js` and the eval use invented text only.
- Slack message text is untrusted data: the model gets no tools, is told messages are data, and returns JSON checked in code. The model cites message references; code builds every link and drops claims without a valid reference.
- **Data sharing (user decision):** internal conversations go to the pinned providers unmasked except for secrets; external conversations (only the `external` unit rule in `config/slack-bus.json`: listed units, names without an internal prefix; Slack's `is_ext_shared` flag does not count) get full masking via `src/mask.js`. Secrets are masked in every conversation. Names are never masked. Only counts of masked items are logged. Quote checks use the masked text. Conversations on the `noCloud` list are never sent to any model.
- **Retention:** message text stays in memory until the digest is written; only the digest file (`data/digests/`, mode 600) persists. Logs and run rows hold counts, usage and cost, never text.
- Run `node scripts/digest-selftest.js` after changing masking, the OpenRouter client, validation or the noise rules, the registry, the pipeline, cap planning, the archive, the DM or send-only client, the healthcheck helper or bot compression, and keep it passing.
- **Schedule (phase 3):** `launchd/com.lab.schedule.slack-digest.plist` runs `node src/digest/run.js --scheduled` daily at 06:00 (the approved exception to the dispatcher rule). Window: since the last success, capped at 72 h. The last-success timestamp (`data/digest-state.json`) is written atomically, only after the digest file is written and the DM was delivered. It pings `~/.lab/healthcheck-url-slack-digest` (checked for mode 600 before the run): success, or `/fail` on any error, deadline or failed delivery, with stats only in the body. The newest 14 digests are kept; older ones are deleted. Scheduled runs print no per-conversation progress.
- **Customer registry:** derived in code from channel names (`src/digest/customers.js`) with git-ignored settings in `config/digest-customers.json` (prefixes, suffixes, filler words, extra keys, aliases, hand assignments; template `config/digest-customers.example.json`). Success channels define customers; other customer channels join by key; unmatched channels are listed and still analyzed, never guessed into a customer. Mentions in Leadership and Internal channels are matched by alias in code (whole word, case-insensitive). After changing the settings, print the registry with `node scripts/digest-customers.js` (names only) and show it to the user before relying on it.
- **Two stages:** stage 1 extracts items per customer conversation; stage 2 makes one synthesis call per customer (headline of at most 20 words, supporting points with references, Leadership flag). Code verifies every reference, builds every link, and decides severity (strongest kept point), the Leadership flag (a kept point cites a Leadership message), the best link and the "bot report" label.
- **Noise rules (user decision):** an item is notable only with evidence of a sentiment or trust change, an incident, a missed deadline or commitment, a commercial signal (contract, renewal, churn, competitor), an escalation or ownership confusion; code drops anything else. Bot hygiene is never attributed to a customer (only counted as skipped). Personnel matters are dropped everywhere. Low-severity items stay in the archive file only, never in the DM or thread.
- **Unit modes** (`unitModes` in `config/slack-digest.json`, the user edits them): full, brief (at most 3 one-line items per unit) or off (only an outage or incident that affects customers). Conversations where the user (`deliverTo`) wrote most messages are left out of unit and brief summaries.
- **Slack delivery:** one Slack app; the user token (`~/.lab/slack-token`) reads, the bot token (`~/.lab/slack-bot-token`, mode 600, Authorization header only) sends. `src/slack-send.js` may call only `conversations.open` and `chat.postMessage` (bot scopes `chat:write`, `im:write`). The only recipient is `deliverTo` in `config/slack-digest.json` (git-ignored; never put the ID in committed files). The DM must come back from `conversations.open` as a 1:1 DM whose user is that ID, or nothing is posted. The top-level message has a hard cap of 1,500 characters (title, Needs attention with at most 5 customers, Watch, Incident, Other units, Skipped); one threaded reply holds per-customer bullets with links (medium and high only) and the model, provider, fallback and cost footer. No file upload. No Slack events, no reading with the bot token, no replies to anyone else. A failed delivery keeps the digest file, does not advance the last-success record, and pings `/fail` with the reason code. Test with `node scripts/digest-dm-test.js` (one invented line, stats only).
- Entry point: `node src/digest/run.js` (code lives in `src/digest/`). Hand runs do not move the last-success timestamp unless `--record` is given. The digest file in `data/digests/` (mode 600) is the only output that may contain message text or model output; never print it in a session or log it. Runs print stats only.
