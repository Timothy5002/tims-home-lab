# Design decisions

| Decision | Why |
|---|---|
| Jobs are files in `jobs/`, not commands in the request | A caller can only pick *which* script runs, never what it does. Adding capability means adding a reviewed file. |
| `spawn` without a shell | No shell means no injection through names or arguments. Jobs receive no arguments at all. |
| Each job runs in its own process group, and the timeout kills the group | Killing only the job's shell left its children running: a `du` stuck on a macOS privacy prompt outlived its `disk-check` run. `spawn` is used because `execFile` ignores the `detached` option that creates the group. |
| Bind to `127.0.0.1`, hardcoded | Nothing off this machine can reach it. No env override, so a config slip cannot expose it. |
| Token in `~/.lab/token`, mode enforced at startup | Keeps the secret out of the repo, plists and logs; the server refuses to start with a loose file. |
| `/health` is the only unauthenticated route | Liveness checks need no secret and reveal nothing. |
| SQLite via built-in `node:sqlite` | No native module to build; one dependency (fastify) in total. |
| Log rejected requests too | Failed auth and bad names are the interesting events for an audit trail. |
| Scheduled runs go through the HTTP API | One code path, one set of guards, and every run lands in the same log. |
| One healthchecks.io check per schedule | A shared check would hide which job failed or went silent. |
| LaunchAgents, not LaunchDaemons | No sudo needed; works because the Mac auto-logs in and never sleeps. |
| LLM tasks run on local Ollama first; other tasks fail with "needs cloud model" | Small, bounded tasks (labels, fields, short summaries) are well within a 7B model, and the text never leaves the Mac. No cloud API key exists yet, so an unknown task fails loudly instead of degrading. |
| The LLM helper reads input on stdin, never as an argument | Arguments show up in `ps` for any local user; stdin does not. The helper also never echoes input in errors. |
| LLM call timeout is 50s, not 60s | The dispatcher kills a job at 60s. Stopping the model call first lets the job print a clear error, and the log shows that instead of a bare "timeout". |
| `keep_alive: 1m` is sent per request instead of setting `OLLAMA_KEEP_ALIVE` on the service | Same effect (the model unloads after a minute idle) without editing the Homebrew-managed service, which an upgrade would overwrite. Ollama used from elsewhere keeps its own default. |
| Structured output (JSON schema) for classify and extract | The model cannot return a label outside the list or a malformed object; the helper still re-checks before printing. |
| Prompt templates live apart from the helper and are checked by `scripts/llm-eval.js` | Templates change more often than the plumbing; the eval shows whether a change helped. The eval is a script, not a test folder, to keep the repo layout. |
| `disk-check` measures `/System/Volumes/Data`, not `/` | `/` is the read-only system snapshot; user data and real free space live on the Data volume |
| `disk-check` fails under 25% **or** under 40 GB free | The percentage suits this drive (25% is about 61 GB); the GB floor still protects if the drive is ever replaced with a much larger one |
| Protected home folders stay unreadable; no Full Disk Access for `node` | Granting it would give every Node script on the Mac full disk access, for a nice-to-have folder list. The free-space check, which is what fails the job, is unaffected |
| `disk-check` measures each home folder with a 5 s cap and a 40 s total budget | Under launchd, macOS can make `du` wait on a privacy prompt forever instead of refusing; the cap turns that into an "unreadable" line instead of a 60 s job kill |
| Plist templates live in `launchd/` and are copied to `~/Library/LaunchAgents/` | The repo is the source of truth; `scripts/install-agent.sh` is the only install path. |
| Slack measurement runs from the terminal, not as a job | Reading a week of history across many channels takes minutes because of Slack's rate limits, far over the 60s job limit. It is a one-off measurement, not a service. |
| Slack measurement keeps counts only | The question is volume, so text is measured in memory a page at a time and dropped. Nothing with message content reaches disk, logs or the terminal. |
| Slack scripts can only call five listed read-only methods | A typo or a future edit cannot turn a measurement tool into something that posts or changes Slack; anything else is refused before a request is made. |
| Tokens estimated as characters / 4 | Good enough to choose between a local and a cloud model, and needs no tokenizer dependency. Real counts differ by model; Slack markup makes it slightly high. |
| Thread replies found with a lookback (default 30 days) | Slack's history only lists a thread inside the window if it started there; scanning further back for threads whose latest reply is in the window catches long-running threads, at the cost of more calls. |
| Slack business-unit rules live in `config/slack-bus.json`, git-ignored, with a tracked example | Channel IDs and unit names are private to the workspace; the example documents the format. `config/` holds settings that are not secrets; secrets stay in `~/.lab/`. |
| `data/` is ignored as a whole, not just `*.db` | Measurement output (channel names, group DM members) must never be committed by accident. |
| `slack-channels.js` keeps only conversations the user is a member of, unless `--all` | In a test run, 215 of 787 conversations were public channels the user was not in. They are unlikely digest sources and each costs a call. Membership comes from `conversations.list`, so no extra Slack method is needed. |
| Slack units have two levels (business unit > sub-group) and rules match by exact name, prefix, glob or regex | Business units are organized that way, and most channel families follow a naming pattern; exact names cover the exceptions. First match wins, with exact names listed first, and every overlap is reported so a broad pattern cannot silently swallow a channel. |
| Group DMs are assigned by ID, with the matched member set recorded beside it | The sidebar shortens group DM names and the same people share many group DMs, so names are ambiguous. The recorded members let a person verify the match and let the script flag a group DM whose members changed. Undecided ones sit in `pendingGroupDms` so they stay visible without being measured. |
| `slack-channels.js --from-cache` re-applies the rules without calling Slack | Listing takes about 13 minutes; editing rules should not need that. It also never reads the token. |
| Unassigned active group DMs can be measured as a separate bucket, outside the main totals (`--unassigned-dms`) | Shows how much text the digest would miss without pretending those DMs belong to a unit. Listing them in the config under a made-up unit would make them look assigned and hide them from the channel report. |
| The Slack digest runs as a standalone launchd schedule, not through the dispatcher (approved exception) | A run takes about 10 minutes (Slack calls are spaced to respect rate limits), far over the 60s job limit. A dispatcher long-job mode would weaken that limit for every job and hold an HTTP request open; the standalone script pings its own healthcheck and writes the same run row instead. |
| Digest window: since the last successful scheduled run, capped at 72 hours | Mondays and missed days are covered without special cases; the cap keeps a long outage from producing one huge, expensive run. |
| Data sharing (user decision): internal conversations unmasked, external ones fully masked, secrets masked everywhere, names never masked | Text from customers and other organizations is the most sensitive, so external conversations (a configured unit rule: listed units, names without an internal prefix) lose emails, phones, long numbers and tokenized URLs. Slack's shared flag is not used, because most shared conversations are shared between the company's own workspaces. Internal conversations stay readable so the analysis is useful. A pasted credential is never useful to a summary, so secrets are masked in every conversation. Names are kept because the digest is about who said what. A `noCloud` list can keep any conversation away from models entirely. |
| Quote checks use the masked text; links point to the original message | The model only ever saw masked text, so that is what a quote must match; the link lets the reader see the real message in Slack. |
| One secret reader (`src/secrets.js`) for the Slack and OpenRouter clients | Same mode-600 rule everywhere and one place to fix it. `src/schedule-run.js` keeps its own copy for now, to avoid touching the running scheduler. |
| Digest settings in `config/slack-digest.json` (git-ignored) | The workspace URL is specific to this workspace; the tracked example documents the format. |
| Phase 1 of the digest is code-only (no model) | It proves fetching, compression, links, retention and runtime on real data without sending anything anywhere, and measures what phase 2 would send. |
| Bot posts are compressed by template in code, keeping alert lines | Bots wrote 54% of characters, mostly repeats. Grouping by bot and template (numbers, IDs, links and dates replaced) cuts that without a model, and listing alert-word instances keeps a real failure from being folded into a count. |
| Hand runs of the digest do not move the "last success" timestamp unless `--record` is given | Testing should never shorten the next scheduled window. |
| Digest thread lookback is 14 days (the measurement used 30) | Each run reads the lookback for every conversation; 14 days still catches older threads that come back to life, at about half the calls. |
| Slack digest models go through OpenRouter: DeepSeek V3.2 pinned to DeepInfra, with Gemini Flash on Google Vertex as a one-time fallback in code | The user chose these. OpenRouter gives one key and one API for both. Pinning each route to one provider with `data_collection: "deny"` and no OpenRouter fallbacks keeps the data path predictable. A different model on a different provider covers outages of the primary. Doing the fallback in code (once, only for timeouts, 5xx, 429 or a provider mismatch) keeps every request to one model and makes the switch visible in the log, the digest header and the healthcheck. Costs come from OpenRouter's own figures, or live endpoint prices, not a hardcoded table. |
| The served provider is checked after every call, from the reply's `provider` field and OpenRouter's generation stats (waiting up to about 30 s) | The stats appeared about 15 s after the reply in testing, so a short wait wrongly failed both routes. Every source that answers must name a pinned provider; if none answers, it counts as a mismatch, which triggers the fallback (primary) or fails the call (secondary). |
| Reasoning off by default; the lowest level for models that cannot turn it off | Extraction needs predictable cost and low temperature. Reasoning tokens are billed as output, so they count toward the output and cost caps. |
| Secret masking: a base64-like match must be one token with no "/", mix upper case, lower case and digits, and not be a UUID or a hyphenated word slug; URL "token" segments must not be word slugs | Run on real data, the looser pattern fired 43 times and every match was a URL or file path (UUIDs, words joined by hyphens), never a credential. Random keys always mix all three character kinds; paths and slugs don't. The specific key patterns (`sk-`, `xox`, `ghp_`, AWS, JWT, long hex) are unchanged. |
| External = only the customer unit's conversations whose names lack an internal prefix; Slack's shared flag is recorded but not used | Slack marks 368 conversations as shared, mostly between the company's own workspaces; treating them as external would have masked internal channels, including per-customer success channels. |
| Digest items must cite message references; code drops uncited items, decides "notable", sanitizes model text and builds every link | The model's job is judgment, not plumbing. Checking references and building links in code means a hallucinated or injected claim cannot carry a link or reach the digest without a real source. |
| Messages go to the model as JSON strings under a "this is data" header, and the prompts say messages are never instructions | Keeps a crafted message from posing as instructions or as another message; the eval includes an injection attempt. |
| Digest prompts have their own eval (`scripts/digest-eval.js`), separate from `scripts/llm-eval.js` | `llm-eval.js` tests the local helper's prompts; the digest prompts run on cloud routes and need side-by-side results per route. |
